Lesson 8 — Human-in-the-Loop

Module 03 · AI Agents · pause, review, approve, deny, modify, and resume safely

Markdown

Human-in-the-loop is an authority boundary

An agent may understand a goal, gather evidence, and propose a sensible action. That does not mean it should be allowed to execute every action autonomously.

The model can recommend or propose. Human approval grants authority for a specific action.

This is most useful where mistakes have meaningful consequences: spending money, sending external communications, changing production, deleting data, publishing content, or acting under uncertainty.

Markdown

There is more than one human-in-the-loop pattern

Approval before action

Pause before a side effect such as a booking, payment, deployment, email, or delete.

Clarification

Ask the user when required information or intent is ambiguous rather than guessing.

Escalation

Hand off when confidence, permissions, risk, or domain policy requires a human decision.

Review after drafting

Let the agent prepare an artifact but require a person to review before publication or execution.

The common design idea is not “put a human everywhere.” It is to identify where human judgment or authority materially improves safety and correctness.

Markdown

Approval should bind to an exact proposal

A weak system asks “Do you approve?” and later executes whatever action currently happens to be in state. A stronger system shows the exact tool, arguments, cost, and consequences, then binds the approval to that exact proposal.

agent proposes action ↓ host validates proposal ↓ risk policy says approval required ↓ create approval request for exact action ↓ PAUSE / persist checkpoint ↓ human approves | denies | modifies ↓ revalidate exact proposal + current state ↓ execute or return decision to agent
Markdown

Theoretical examples

Travel: the assistant may search hotels autonomously, but a non-refundable A$310 booking requires approval before purchase.

Email: the agent may draft a reply, but sending it externally requires approval if the message is consequential.

Engineering: an incident agent may inspect logs and recommend a rollback, but production rollback remains gated by a human or an existing change-management policy.

Clarification: “Book me a flight to Sydney next Friday” is incomplete if the departure city or acceptable price range is unknown. Asking is safer than inventing.

Example 1 — represent the proposed action explicitly

The agent does not call book_hotel directly. It creates an application-owned proposal that can be inspected and fingerprinted.

In [ ]
from dataclasses import dataclass, field
from enum import Enum
import hashlib
import json
from typing import Any

class RiskLevel(str, Enum):
    LOW = "low"
    HIGH = "high"

@dataclass(frozen=True)
class ActionProposal:
    tool: str
    arguments: dict[str, Any]
    summary: str
    risk: RiskLevel

def proposal_fingerprint(proposal: ActionProposal) -> str:
    payload = {
        "tool": proposal.tool,
        "arguments": proposal.arguments,
    }
    canonical = json.dumps(payload, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(canonical.encode("utf-8")).hexdigest()

proposal = ActionProposal(
    tool="book_hotel",
    arguments={
        "city": "Melbourne",
        "hotel": "Harbour View",
        "nights": 1,
        "total_aud": 310,
        "refundable": False,
    },
    summary="Book one non-refundable night for A$310.",
    risk=RiskLevel.HIGH,
)

print(proposal_fingerprint(proposal)[:12])

The fingerprint is not an authorization mechanism by itself. It is a simple way to bind a recorded decision to the exact tool arguments that were reviewed.

Markdown

Risk policy belongs to the host

Do not ask the model whether its own action needs approval. Use deterministic policy where possible.

In [ ]
READ_ONLY_TOOLS = {"search_hotels", "get_weather", "get_sun_times"}
SIDE_EFFECT_TOOLS = {"book_hotel", "send_email", "deploy_release", "delete_record"}

def requires_approval(proposal: ActionProposal) -> bool:
    if proposal.tool in SIDE_EFFECT_TOOLS:
        return True
    if proposal.risk == RiskLevel.HIGH:
        return True
    return False

print(requires_approval(proposal))

In production the policy may also consider cost thresholds, user role, tenant policy, environment, reversibility, data sensitivity, or previous delegated authority.

Example 2 — create a resumable approval request

An approval is application state. It needs an identifier, proposal fingerprint, lifecycle status, and enough context for a person to decide.

In [ ]
class ApprovalStatus(str, Enum):
    PENDING = "pending"
    APPROVED = "approved"
    DENIED = "denied"

@dataclass
class ApprovalRequest:
    id: str
    proposal: ActionProposal
    proposal_hash: str
    status: ApprovalStatus = ApprovalStatus.PENDING
    decided_by: str | None = None
    note: str | None = None

def create_approval_request(request_id: str, proposal: ActionProposal) -> ApprovalRequest:
    if not requires_approval(proposal):
        raise ValueError("This proposal does not require approval")
    return ApprovalRequest(
        id=request_id,
        proposal=proposal,
        proposal_hash=proposal_fingerprint(proposal),
    )

approval = create_approval_request("approval-001", proposal)
approval
Markdown

Pause means stop executing, not block a thread forever

A production agent may wait minutes, hours, or days for approval. Do not keep an in-memory Python loop sleeping until a person clicks a button. Persist the checkpoint and return a status such as WAITING_FOR_APPROVAL.

running agent ↓ approval required ↓ persist: - goal - current state - exact proposal - approval request - budgets / expiry ↓ return WAITING_FOR_APPROVAL ...later... decision arrives ↓ load checkpoint ↓ revalidate ↓ resume
Markdown

Approve, deny, and modify are different outcomes

Approval should not be the only human response. A person may deny the action or ask for a modified proposal, such as a refundable room under A$250.

In [ ]
def decide(
    request: ApprovalRequest,
    *,
    status: ApprovalStatus,
    decided_by: str,
    note: str | None = None,
) -> None:
    if request.status != ApprovalStatus.PENDING:
        raise ValueError("Approval request has already been decided")
    request.status = status
    request.decided_by = decided_by
    request.note = note

decide(
    approval,
    status=ApprovalStatus.DENIED,
    decided_by="demo-user",
    note="Find a refundable option under A$250.",
)

print(approval.status, approval.note)

A modification is usually represented as a denial plus new constraints. The agent then creates a new proposal and, if needed, a new approval request. Do not silently mutate an already approved action.

Example 3 — execute only the approved proposal

Before execution, re-check that the proposal still matches the one that was approved and that the approval is valid.

In [ ]
def simulated_book_hotel(arguments: dict[str, Any]) -> dict[str, Any]:
    # Simulation only: no real booking is performed.
    return {
        "booking_id": "SIM-1234",
        "status": "booked",
        **arguments,
    }

def execute_approved(
    request: ApprovalRequest,
    proposal_to_execute: ActionProposal,
) -> dict[str, Any]:
    if request.status != ApprovalStatus.APPROVED:
        raise PermissionError("Action has not been approved")
    if proposal_fingerprint(proposal_to_execute) != request.proposal_hash:
        raise PermissionError("Proposal changed after approval")
    if proposal_to_execute.tool != "book_hotel":
        raise ValueError("Unsupported demo action")
    return simulated_book_hotel(proposal_to_execute.arguments)

Even after approval, production systems should revalidate current conditions: price, inventory, permissions, environment, expiry, and any facts that may have changed while waiting.

Markdown

Approval has scope and expiry

Exact action

“Approve this A$310 booking” should not become “approve any travel purchase.”

Identity

Record who approved and whether that person had authority to approve.

Time

Approval may expire. A price or deployment state can change while the agent is paused.

Context

Environment, tenant, account, resource version, or change ticket may be part of the approval boundary.

Markdown

Human review is not a substitute for deterministic safety

Do not send every unsafe proposal to a human. Invalid, disallowed, or unauthorised actions should be rejected by policy before an approval request is created.

Approval sits after validation and policy checks. A human should review a meaningful, allowed proposal—not compensate for missing authentication, schema validation, tenant isolation, or hard safety rules.

Markdown

What the human should see

An approval UI should make the decision understandable without reading hidden prompts or raw traces. Show the proposed action, important arguments, side effects, cost or scope, relevant evidence, why approval is required, and clear approve/deny controls. For high-impact actions, make consequences explicit.

For an engineering rollback, for example: service, environment, version, expected impact, evidence, change/ticket reference, and rollback target are more useful than “Agent wants to call rollback_service.”
