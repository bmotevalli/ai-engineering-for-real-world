Lesson 10 — Build a Real Agent from Scratch in Python

Module 03 · AI Agents · combine the pieces before introducing a framework

Markdown

What makes this lesson different?

Earlier lessons isolated one mechanism at a time. Now we connect them into one small agent and keep every important boundary visible.

The model owns bounded decisions; the host owns tools, state, budgets, retry policy, validation, approvals, and execution authority.

The goal is not to create the shortest code. The goal is to understand the architecture that frameworks later compress.

Markdown

Scenario

Plan a family-friendly afternoon in Melbourne tomorrow. Check the weather and daylight. Prefer outdoor activities if conditions are suitable. If you recommend something that needs a reservation, ask before reserving it for three people.

The agent has live weather and sun-time tools, a small deterministic activity catalogue, and a simulated reservation tool. The reservation is a side effect and cannot execute without approval.

Markdown

Architecture

selected memory + goal ↓ optional external plan ↓ ┌──────────── host-owned loop ────────────┐ │ check budgets │ │ ↓ │ │ model chooses next action │ │ ↓ │ │ validate allowlist + arguments │ │ ↓ │ │ detect repeated action │ │ ↓ │ │ read-only tool? → retry safely → observe │ │ │ │ │ no │ │ ↓ │ │ side effect → WAITING_FOR_APPROVAL │ └──────────────────────────────────────────┘

Nothing in this architecture gives the model direct Python execution or permission to expand its own authority.

Markdown

Reusable host objects

The implementation defines explicit application types instead of hiding control state in prompts:

Tool

Name, description, schema, handler, side-effect flag.

AgentState

Goal, provider protocol items, observations, action fingerprints, usage, plan, selected memory.

RunBudget / RunUsage

Host-owned limits and counters.

ActionProposal / AgentResult

Explicit approval checkpoint and structured run outcome.

Markdown

The tool registry

Three tools are read-only: get_weather, get_sun_times, and search_activities. reserve_activity is marked as a side effect. The model sees schemas; only host code holds the executable handlers.

Markdown

Selected memory, not unlimited history

The example injects stable travel preferences such as family-friendly and an outdoor preference. Old weather observations or irrelevant conversations are not automatically carried forward.

In [ ]
memory = {
    "travel_style": "family-friendly",
    "outdoor_preference": "prefer outdoors when weather is suitable",
}
Markdown

Planning remains optional

For this broad goal we enable a concise external plan. For a simple question such as “What is tomorrow's Melbourne weather?”, planning should remain off. Planning is orchestration overhead, not a badge of sophistication.

Markdown

Budgets before autonomy

The runner receives a small RunBudget. Step limits, tool-call limits, retry attempts, and repeated-action limits are host policy. The model cannot increase them.

In [ ]
from agent import RunBudget

budget = RunBudget(
    max_steps=6,
    max_tool_calls=6,
    max_same_action=2,
    retry_attempts=3,
)
Markdown

The integrated run

The main notebook calls run_agent(...). The exact tool sequence may vary because the model owns the bounded decision. What should not vary are the host boundaries.

In [ ]
from agent import run_agent

goal = (
    "Plan a family-friendly afternoon in Melbourne tomorrow. "
    "Check the weather and daylight. Prefer outdoor activities if conditions are suitable. "
    "If you recommend something that needs a reservation, ask before reserving it for three people."
)

result = run_agent(
    goal,
    budget=budget,
    memory_context=memory,
    use_planning=True,
)

print("status:", result.status.value)
print("reason:", result.stop_reason.value)
print("steps:", result.state.usage.steps)
print("tool calls:", result.state.usage.tool_calls)
Markdown

Approval is part of control flow

If the model chooses a no-reservation activity, the run may complete normally. If it requests reserve_activity, the host does not execute it. The result becomes WAITING_FOR_APPROVAL with the exact pending proposal.

model requests reserve_activity ↓ validate tool + arguments ↓ side_effect == True ↓ create exact ActionProposal ↓ RETURN WAITING_FOR_APPROVAL ↓ human approve / deny ↓ append observation ↓ resume agent loop
In [ ]
from agent import RunStatus, resume_after_approval

if result.status == RunStatus.WAITING_FOR_APPROVAL:
    resumed = resume_after_approval(
        result,
        approved=True,  # try False as well
        budget=budget,
    )
    print(resumed.status.value)
    print(resumed.answer)
Markdown

Why the trace matters

A final answer is not enough for production debugging. The host separately stores structured observations: which tool ran, with which arguments, and what happened. That is easier to log, test, evaluate, and inspect than reconstructing execution from prose.

In [ ]
for item in result.state.observations:
    print(item["tool"], item["arguments"])
    print(item["observation"])
Markdown

The reusable implementation

The full code is in agent.py. It intentionally remains explicit: tool registry, argument validation, retry wrapper, state, budgets, repeated-action detection, model calls, approval pause, and resume are visible as normal Python.

A small test_agent.py covers deterministic pieces such as fingerprint stability, argument validation, activity search, and approval binding. The notebook does not try to unit-test itself.

Markdown

What is still intentionally missing?

Durable checkpoints

Approval state is in memory for the lesson. Production would persist it.

Full usage accounting

Step/tool budgets are integrated; richer token, cost, deadline, and cancellation accounting would be added around provider calls.

Strong typed validation

The lesson keeps schemas readable. Production systems may use typed domain models and more precise validation.

Evaluation + observability

Systematic traces, metrics, test datasets, and agent evaluation belong in later modules.

These omissions are useful preparation for the next lesson: we can now judge frameworks against concrete responsibilities rather than marketing abstractions.

Markdown

Engineering extension

The travel tools can be replaced with check_service_health, get_pod_logs, get_kubernetes_events, and a side-effecting rollback_deployment. The host architecture remains the same: read-only investigation can be agentic, while mutation is validated, bounded, and approval-gated.
