Lesson 1

What is an AI Agent?

Start with the control-flow decision that separates an ordinary LLM application from an agent.

Normal LLM application

This is simply an LLM call. It is not an agent:

User → LLM → Answer
response = model("Explain Kubernetes")

The model receives input and generates output, but it is not deciding what actions should happen next.

From a question to a goal

Investigate why my Kubernetes deployment is failing and tell me what I should fix.

A useful AI system may need to inspect deployments, pods, events, logs, configuration, and evidence before deciding what to do next.

Engineering definition of an AI agent

An AI agent is a system where an LLM participates in choosing the next action required to achieve some goal.

The agent loop

Observe
   ↓
Decide
   ↓
Act
   ↓
Observe result
   ↓
Decide again

The loop continues until the goal is completed, the agent cannot progress, or a stopping condition is reached.

Workflow vs agent

Deterministic workflow

The application determines the execution order in advance.

VS

Agent

The model participates in choosing what action should happen next based on what it has observed.

The important question is:Where is the model making an autonomous control-flow decision?

Four core components of an agent

1

Goal

An agent works toward a goal.

2

LLM

The LLM participates in decisions.

3

Tools

Tools expose external capabilities.

4

State

State captures what the agent has learned and done.

Agent autonomy is a spectrum

DeterministicAutonomous
LLM callFixed workflowTool selectionIterative tool selectionPlanningPlan adaptationLong-running autonomous agent
Engineering principleUse the minimum level of autonomy necessary to solve the problem well.

State and Memory

Separate what the current agent run needs from what the application deliberately remembers across future runs.

The key distinction

State is what the current run needs. Memory is what the application deliberately carries into a future run.

The distinction is about lifetime and ownership, not just storage. State normally exists to complete the current task. Memory exists because the application has decided some information should survive and may be useful later.

Four concepts that are easy to confuse

Context

Everything supplied to the current model call: instructions, current request, selected history, tool observations, and retrieved memory.

Conversation history

The chronological user/assistant exchange. It can be part of context, but it is not the same thing as authoritative application state.

State

The structured information needed to continue the current task correctly: goal, progress, observations, budgets, permissions, and protocol items.

Memory

Information deliberately persisted beyond the current run and retrieved later when relevant.

Think in lifetimes

A useful question is: if this task finished now, should this information still exist for a future task?

Usually state

Current weather result, active tool call, current hypothesis, remaining step budget, temporary error, current workflow status.

Potential memory

Preferred language, dietary preference, project deployment region, recurring travel preference, or another stable fact with clear future value.

Example: a deployment-investigation agent may need pod names, logs, and a current hypothesis during the incident. Those facts are useful working state, but replaying them months later into an unrelated investigation would usually be stale noise.

Memory has a lifecycle

candidate information
       ↓
Should it outlive this task?
   ├── no  → keep as state → discard when done
   └── yes → validate + scope + persist
                         ↓
                 retrieve when relevant
                         ↓
                  revise / expire / delete

Persistence alone does not make a useful memory system. The application also needs rules for scope, retrieval, relevance, correction, deletion, retention, and authority.

Theoretical example — travel assistant

For the question “Plan my Melbourne day tomorrow”, the assistant may use tomorrow's rain probability and sunset time as current state. But a preference such as “I prefer vegetarian restaurants and morning departures” may be worth remembering across future sessions. The two types of information belong to different lifecycles even though both may appear in the same model context today.

Production principle

Do not treat unlimited conversation history as memory

Long-term memory should be selected, scoped, revisable, and deletable. Persisting everything increases token cost, stale-context risk, privacy exposure, and the chance that malicious instructions survive far beyond the request that introduced them.

Planning

Decide when an agent should create an explicit plan, how the plan lives in state, and when new evidence should revise it.

Core idea

A plan is an explicit, revisable description of intended work — not permission to execute it.

A reactive agent chooses one action at a time. Planning adds a separate artifact: a concise task list that can expose dependencies, ordering, progress, and work that may need approval before execution.

When planning helps

  • Several dependent information-gathering steps.
  • Expensive or irreversible actions.
  • Need for progress visibility or user review.
  • Tasks where observations may invalidate later work.
  • Do not plan merely because the system is agentic.
  • Simple one-tool questions are usually better without a plan.
  • Known fixed sequences are often deterministic workflows.
  • Planning adds model calls, latency, state, and failure modes.

Planning is not chain-of-thought

The useful artifact is a short external task list: what needs to happen, which allowed action it maps to, and what evidence is needed. The application does not need private model reasoning in order to execute safely.

The plan-execute-replan pattern

goal
 ↓
create concise plan
 ↓
validate plan
 ↓
execute next step
 ↓
record observation + status
 ↓
remaining plan still valid?
 ├── yes → continue
 └── no  → revise / skip (bounded)
 ↓
final synthesis

The plan is working state. The host owns allowed actions, step status, tool execution, and limits on replanning.

Engineering extension

For “Investigate why checkout latency increased”, an explicit plan might inspect service metrics, dependency health, and the current deployment before synthesis. If the first observation reveals a known database incident, the host can skip or revise steps that no longer add value.

Production principle

Planning increases autonomy, not authority

A model-generated plan is untrusted application input. Validate allowed actions and plan size before execution, and bound how often the system can replan.

Checkpoint

Should every agent create a plan first?

No. Planning is useful only when decomposition or coordination adds value. A one-tool weather lookup usually needs no explicit plan.

When should a plan change?

When new observations materially invalidate assumptions, make remaining work unnecessary, or block the current route. Replanning after every step is usually wasteful.

Error Handling and Retries

Classify failures, retry only what is safe, and keep recovery bounded and observable.

Core idea

The host classifies failures and owns retry policy. The model decides what to do only after the host returns a final success or failure observation.

Agent systems fail at several layers: model providers, networks, tools, validation, permissions, and domain rules. Treating every error as “try again” creates latency, duplicate side effects, and uncontrolled loops.

Classify before retrying

Transient

Timeouts, connection resets, rate limits, and many 5xx responses may succeed on a later attempt.

Validation

Malformed tool arguments or unsupported values should normally fail fast rather than repeat unchanged.

Domain

No availability, ineligible account, or missing resource may be a valid business outcome rather than infrastructure failure.

Permission

Authentication, authorisation, or approval failures require changed authority, not blind retries.

Retry at the narrowest layer

agent loop
  ↓
provider call ───── retry provider failure here
  ↓
tool adapter ────── retry network/API failure here
  ↓
business action ─── protect side effects with idempotency
  ↓
one final observation returned to the agent

A low-level HTTP timeout should not automatically replay the entire agent step. Keep provider retries, tool retries, and agent reasoning steps as separate budgets.

Example 1 · Deterministic retry

Recover from a flaky read-only weather lookup

A simulated weather tool fails twice with a transient timeout and then succeeds. The host uses bounded exponential backoff and a retry predicate, making the recovery path deterministic and testable.

Example 2 · Agent observation

Turn exhausted recovery into structured failure state

After retryable attempts are exhausted, the host produces one structured failure observation. The model can then choose an alternate tool, ask for different input, provide a partial answer, or stop—without controlling the low-level retry loop.

Side effects change the rules

Timeout does not mean “nothing happened”

If a booking, payment, email, deployment, or deletion may already have succeeded before the response was lost, blind retries can duplicate the side effect. Use idempotency keys or status checks before retrying side-effecting tools.

Checkpoint

Should the model decide whether a timeout is retryable?

No. Retryability is infrastructure/application policy. The model may decide what to do after the host returns a final failure observation.

Are agent step budgets and retry budgets the same?

No. One agent step can contain several low-level attempts. Track and bound both separately so a small reasoning budget cannot hide a large number of external requests.

Stopping Conditions and Budgets

Make termination explicit so an agent cannot continue indefinitely just because the model keeps proposing actions.

Core idea

The model may decide that it is finished. The application decides whether it is allowed to continue.

A final model answer is only one stopping condition. Production agents also need host-controlled ceilings for time, steps, external actions, tokens, cost, repeated actions, lack of progress, and authority boundaries.

Budgets are independent

Steps

Bound model decision turns.

Tool calls

Bound external actions separately from reasoning steps.

Time / cost

Enforce wall-clock, token, and spend ceilings.

Progress

Stop obvious repetition and runs that keep consuming resources without adding evidence.

A budget is a ceiling, not a target. The agent should stop as soon as the goal is satisfied.

Check before expensive work

before model call
  ├── deadline?
  ├── step budget?
  └── token / cost budget?
        ↓
model decides
        ↓
before tool execution
  ├── tool-call budget?
  ├── repeated action?
  └── authority available?
        ↓
observation
        ↓
progress made?
        ↓
continue, complete, or terminate with reason
Example 1 · Run budget

Track usage across several resource dimensions

A deterministic RunBudget defines step, tool, time, token, cost, repetition, and no-progress limits. A separate RunUsage records what the current run has consumed.

Example 2 · Loop detection

Stop repeated actions before wasting another tool call

The host fingerprints a tool name plus normalized arguments. Repeated requests can be stopped before execution, while domain-specific progress signals distinguish legitimate polling from a stuck loop.

Example 3 · Graceful termination

Return a structured stop reason instead of losing the run

A RunResult distinguishes successful completion from timeout, cost exhaustion, repeated action, no progress, or another host-enforced stop. The caller can then return a partial answer, save a checkpoint, or escalate.

Production principle

Max steps alone is not enough

One model step can hide provider retries, several tool calls, or an expensive request. Keep model steps, low-level retries, external actions, time, tokens, and cost visible as separate controls.

Checkpoint

Should an agent try to use its whole budget?

No. Budgets are upper bounds. Once the goal is satisfied, continuing simply because resources remain is wasteful and can increase risk.

Is repeating a tool call always a loop?

No. Polling can be legitimate when observations change. Repetition becomes suspicious when the same action and arguments repeatedly produce no meaningful new state.

Human-in-the-Loop

Add explicit human authority where an agent reaches consequential, ambiguous, or policy-sensitive decisions.

Core idea

The model can recommend or propose. Human approval grants authority for a specific action.

Human-in-the-loop is most valuable at boundaries where the cost of a mistake is meaningful: spending money, sending external communication, changing production, deleting data, publishing content, or acting under uncertainty.

Four common patterns

Approval

Pause before a consequential side effect.

Clarification

Ask when required intent or information is ambiguous rather than guessing.

Escalation

Hand off when risk, permissions, or domain policy requires human judgment.

Review

Let the agent prepare an artifact but require a person to review before publication or execution.

Approval must bind to the exact proposal

agent proposes action
        ↓
host validates + applies risk policy
        ↓
approval required?
        ↓
persist exact proposal + checkpoint
        ↓
WAITING_FOR_APPROVAL
        ↓
approve | deny | modify
        ↓
revalidate current state
        ↓
execute exact approved action or resume agent

A vague “yes” should not become blanket permission. The reviewed tool, arguments, scope, and important consequences should be part of the approval boundary.

Engineering extension

An incident agent may inspect metrics, logs, and deployments autonomously, then propose a production rollback. The approval should show the environment, current version, rollback target, evidence, expected impact, and change reference before execution is allowed.

Production principle

Human review does not replace deterministic safety

Reject invalid, forbidden, or unauthorised actions before creating an approval request. Authentication, schema validation, tenant isolation, hard policy, idempotency, and permissions remain application responsibilities.

Checkpoint

Should every side effect always require a human?

Not necessarily. Approval policy should reflect risk, reversibility, cost, delegated authority, user preferences, and organisational controls. The important point is that authority is explicit rather than inferred from model confidence.

What if the human wants a modified action?

Create a new proposal under the new constraints. Do not silently mutate an already reviewed or approved action and reuse the old approval.
