Lesson 6 — Error Handling and Retries

Module 03 · AI Agents · classify failures, retry only what is safe, and preserve control

Markdown

Why error handling is part of agent design

An agent combines probabilistic model decisions with networks, APIs, databases, and tools. Failures are normal: a provider may rate-limit you, an HTTP call may time out, a tool may reject input, or a domain rule may make the requested action impossible.

Do not let the model decide whether infrastructure should be retried. The host classifies the failure and applies a bounded recovery policy.

The model may decide what to do after a failure becomes an observation, but retry mechanics belong to deterministic application code.

Markdown

First classify the failure

Transient infrastructure

Timeouts, connection resets, 429 rate limits, and many 5xx responses. Often retryable with a bounded delay.

Permanent request / validation

Malformed arguments, unsupported tool names, invalid dates, schema failures. Retrying the same request usually repeats the same failure.

Domain failure

No seats available, account not eligible, city not found, resource already deleted. The operation worked correctly; the requested outcome is unavailable.

Permission / authentication

401, 403, missing scope, approval required. Blind retries are usually wrong; fix authority or escalate.

A useful retry policy starts with a simple question: is there a realistic chance that repeating the exact same operation shortly will succeed?

Markdown

Where retries belong

agent loop ↓ model call ────────────── retry provider call here ↓ tool request ↓ tool adapter ─────────── retry network/API call here ↓ business operation ───── do not blindly repeat side effects ↓ observation ↓ agent decides again

Retry at the narrowest layer that owns the failing operation. Retrying the entire agent step because one HTTP request timed out can duplicate model calls, tool calls, or side effects.

Example 1 — bounded retries around a flaky read-only tool

We start with a deterministic simulation so the behavior is reproducible. The operation fails twice with a transient timeout, then succeeds. This is safer to learn from than hoping a real API happens to fail while you watch.

In [ ]
from dataclasses import dataclass
import time
from typing import Callable, TypeVar

T = TypeVar("T")

class TransientToolError(RuntimeError):
    pass

class PermanentToolError(RuntimeError):
    pass

@dataclass(frozen=True)
class RetryPolicy:
    max_attempts: int = 3
    base_delay_seconds: float = 0.25
    max_delay_seconds: float = 2.0

def retry_call(
    operation: Callable[[], T],
    *,
    policy: RetryPolicy,
    is_retryable: Callable[[Exception], bool],
    sleep: Callable[[float], None] = time.sleep,
) -> T:
    for attempt in range(1, policy.max_attempts + 1):
        try:
            return operation()
        except Exception as exc:
            if not is_retryable(exc) or attempt == policy.max_attempts:
                raise
            delay = min(
                policy.base_delay_seconds * (2 ** (attempt - 1)),
                policy.max_delay_seconds,
            )
            print(f"attempt {attempt} failed: {exc}; retrying in {delay:.2f}s")
            sleep(delay)

    raise AssertionError("unreachable")
Markdown

Simulate a transient failure

Only the exception type marked transient is retryable. The host does not ask the LLM whether to try again.

In [ ]
attempts = 0

def flaky_weather_lookup() -> dict:
    global attempts
    attempts += 1
    if attempts < 3:
        raise TransientToolError("weather API timed out")
    return {"city": "Melbourne", "rain_probability_percent": 35}

result = retry_call(
    flaky_weather_lookup,
    policy=RetryPolicy(max_attempts=3, base_delay_seconds=0),
    is_retryable=lambda exc: isinstance(exc, TransientToolError),
    sleep=lambda _: None,
)

print(result)
print("attempts:", attempts)

Expected result: the tool succeeds on attempt 3. The retry count is bounded and observable.

Markdown

Permanent failures must fail fast

If the tool receives an invalid date or an unsupported city identifier, waiting 250 ms and sending the same invalid request again does not improve anything.

In [ ]
attempts = 0

def invalid_request() -> dict:
    global attempts
    attempts += 1
    raise PermanentToolError("target_date must be YYYY-MM-DD")

try:
    retry_call(
        invalid_request,
        policy=RetryPolicy(max_attempts=5, base_delay_seconds=0),
        is_retryable=lambda exc: isinstance(exc, TransientToolError),
        sleep=lambda _: None,
    )
except PermanentToolError as exc:
    print("failed immediately:", exc)
    print("attempts:", attempts)

Expected result: exactly one attempt.

Markdown

Backoff and jitter

Exponential backoff reduces pressure on a struggling dependency. In production, add a small random jitter so many workers do not retry at exactly the same moments.

attempt 1 fails → wait ~0.25s attempt 2 fails → wait ~0.50s attempt 3 fails → wait ~1.00s ... cap the delay and cap the attempts

Respect provider hints such as Retry-After when available. A retry policy is a resource policy too: it consumes latency, tokens, requests, and user patience.

Example 2 — convert final tool failure into an observation

After retryable recovery is exhausted, the agent should receive a structured failure observation. That lets the model choose a useful next action without giving it control of the retry loop.

In [ ]
def run_tool_with_policy(name: str, operation: Callable[[], dict]) -> dict:
    try:
        data = retry_call(
            operation,
            policy=RetryPolicy(max_attempts=3),
            is_retryable=lambda exc: isinstance(exc, TransientToolError),
        )
        return {"ok": True, "tool": name, "data": data}
    except PermanentToolError as exc:
        return {
            "ok": False,
            "tool": name,
            "error": {
                "kind": "validation",
                "retryable": False,
                "message": str(exc),
            },
        }
    except TransientToolError as exc:
        return {
            "ok": False,
            "tool": name,
            "error": {
                "kind": "transient_exhausted",
                "retryable": False,
                "message": str(exc),
            },
        }

The final observation says retrying at this layer is finished. The model can now answer with a limitation, choose another tool, or ask the user for different input.

Markdown

Provider calls need their own retry boundary

A model API can fail before any tool is selected. Keep provider retries separate from tool retries. With the OpenAI SDK, retryable examples include connection errors, timeouts, rate limits, and some server errors.

In [ ]
from openai import (
    APIConnectionError,
    APITimeoutError,
    InternalServerError,
    RateLimitError,
)

RETRYABLE_PROVIDER_ERRORS = (
    APIConnectionError,
    APITimeoutError,
    InternalServerError,
    RateLimitError,
)

def call_model_with_retry(client, **kwargs):
    return retry_call(
        lambda: client.responses.create(**kwargs),
        policy=RetryPolicy(max_attempts=3, base_delay_seconds=0.5),
        is_retryable=lambda exc: isinstance(exc, RETRYABLE_PROVIDER_ERRORS),
    )

Do not hide unlimited SDK retries under your own retries. Know which layer retries, and cap the combined behavior.

Markdown

Side effects change the rules

Danger: if a request timed out after the server created a booking, retrying the same call may create a second booking.

Read-only operations are comparatively easy to retry. Side-effecting operations need idempotency or a way to check whether the first attempt actually succeeded.

create_booking(
    trip_id="trip-123",
    idempotency_key="agent-run-42:step-3"
)

For payments, bookings, emails, deployments, and destructive actions, design idempotency before adding retries.

Markdown

Retry budget versus agent step budget

These are different controls. One agent step may contain several low-level retry attempts, but the model should not see every timeout as a new reasoning step.

agent step 2 └── weather tool ├── HTTP attempt 1 → timeout ├── HTTP attempt 2 → timeout └── HTTP attempt 3 → success ↓ one observation returned to the agent

Keep both budgets visible. Otherwise a “5-step agent” can secretly perform dozens of external requests.

Markdown

Production failure policy

Bound everything

Attempts, total deadline, per-request timeout, tool calls, model steps, and cost.

Log the classification

Record operation, failure kind, attempt number, elapsed time, and final outcome without leaking secrets.

Preserve cause

Return user-safe messages to the model while retaining diagnostics for operators.

Degrade deliberately

Fallback, alternate tool, partial answer, human escalation, or a clear failure may all be better than another retry.
