Lesson 9 — Deterministic Workflows vs Agents

Module 03 · AI Agents · choose the minimum autonomy that solves the problem well

Markdown

The architecture question

By now we can build an agent loop, manage state, plan, retry, enforce budgets, and pause for approval. The next question is more important than any of those mechanisms:

Should this problem be an agent at all?

Agentic control is useful when the correct sequence of actions cannot be fully known in advance and the model can use observations to choose a better next step. If the sequence is already known, ordinary software is often clearer, cheaper, faster, and easier to test.

Markdown

Three architecture shapes

Deterministic workflow

validate → fetch → transform → persist → notify

The application owns the sequence and branching rules.

Agent

observe → model decides → act → observe → ...

The model participates in choosing the next action.

Hybrid

deterministic guardrails ↓ bounded agentic decision ↓ deterministic validation / execution

Only the uncertain part gets model autonomy.

LLM inside a workflow

fixed step → classify/summarize with LLM → fixed step

Using an LLM does not automatically make the system an agent.

Markdown

A practical decision framework

QuestionPushes toward workflowPushes toward agent
Is the action sequence known?Yes, stable and explicitNo, depends on observations
Are branches easy to encode?Small finite rule setMany fuzzy or open-ended possibilities
Are actions consequential?Prefer deterministic control around themAgent may propose, but execution still gated
Is evaluation objective?Rules/tests can verify each stepQuality requires semantic judgment
What is the cost of extra autonomy?Latency/cost/risk outweigh benefitAdaptive reasoning materially improves results

The answer is often hybrid: deterministic software for known rules and side effects, with a bounded model decision where ambiguity actually exists.

Markdown

Theoretical examples

Password reset: identity checks, token issuance, expiry, and password update are a deterministic workflow. An LLM might explain the process, but should not invent the security flow.

Invoice ingestion: upload → virus scan → parse → validate required fields → save is mostly deterministic. An LLM may extract ambiguous text, but orchestration can remain fixed.

Incident investigation: the useful next query may depend on metrics, logs, deployment history, and new evidence. This is a stronger candidate for bounded agentic investigation.

Travel booking: research and comparison may benefit from agentic exploration; payment and booking should remain deterministic and approval-gated.

Markdown

Main example — design the same travel task three ways

Find a suitable hotel for one night in Melbourne under A$300, prefer refundable options, and book only after I approve.

The task contains both predictable rules and open-ended choice. We will model deterministic, agentic, and hybrid versions to make the trade-off visible.

Markdown

1. Deterministic workflow

If our product has a known search API and explicit ranking criteria, ordinary code may be enough.

In [ ]
from dataclasses import dataclass

@dataclass(frozen=True)
class Hotel:
    name: str
    total_aud: int
    refundable: bool
    rating: float

HOTELS = [
    Hotel("Central Stay", 260, True, 4.2),
    Hotel("River Rooms", 220, False, 4.6),
    Hotel("Garden Hotel", 290, True, 4.5),
    Hotel("Premium Suites", 360, True, 4.8),
]

def choose_hotel_deterministically(hotels: list[Hotel], max_price: int) -> Hotel:
    eligible = [hotel for hotel in hotels if hotel.total_aud <= max_price]
    if not eligible:
        raise ValueError("No hotel fits the budget")

    return max(
        eligible,
        key=lambda h: (h.refundable, h.rating, -h.total_aud),
    )

choice = choose_hotel_deterministically(HOTELS, max_price=300)
choice

The policy is explicit: filter by hard budget, then prefer refundable, then rating, then lower price. There is little value in asking a model to rediscover this logic on every run.

Markdown

2. Agentic selection

Suppose suitability is open-ended: “quiet but central, good for a child, close to evening activities, avoid nightlife-heavy streets.” The relevant trade-offs may be harder to encode as a small ranking function. A model can compare structured observations and choose what additional information it needs.

goal ↓ search hotels ↓ model compares options ↓ needs neighbourhood context? ├── yes → inspect area └── no ↓ needs cancellation details? ├── yes → fetch policy └── no ↓ recommend option

This is genuinely more agentic because the model participates in deciding which evidence to gather next.

Markdown

3. Hybrid design

For the full booking product, neither extreme is ideal.

deterministic: validate dates, budget, travellers ↓ agentic: research + compare ambiguous preferences ↓ deterministic: enforce hard price/policy constraints ↓ human approval: exact proposed booking ↓ deterministic: idempotent booking API call + audit

The model gets autonomy only where semantic judgment is useful. Authority and invariants remain outside the model.

Markdown

Represent architecture choice explicitly

A small classifier can help teams discuss design before implementation. This is not something the model must decide at runtime; it is an engineering design aid.

In [ ]
from enum import Enum

class Architecture(str, Enum):
    WORKFLOW = "workflow"
    AGENT = "agent"
    HYBRID = "hybrid"

@dataclass(frozen=True)
class TaskCharacteristics:
    sequence_known: bool
    open_ended_decisions: bool
    consequential_side_effects: bool
    semantic_judgment_needed: bool

def recommend_architecture(task: TaskCharacteristics) -> Architecture:
    if task.open_ended_decisions and task.consequential_side_effects:
        return Architecture.HYBRID
    if task.open_ended_decisions or (
        task.semantic_judgment_needed and not task.sequence_known
    ):
        return Architecture.AGENT
    return Architecture.WORKFLOW

examples = {
    "password_reset": TaskCharacteristics(True, False, True, False),
    "incident_investigation": TaskCharacteristics(False, True, False, True),
    "travel_booking": TaskCharacteristics(False, True, True, True),
}

for name, task in examples.items():
    print(name, "→", recommend_architecture(task).value)

The point is the questions, not this toy scoring rule. Real architecture reviews should discuss failure modes, observability, permissions, evaluation, latency, and reversibility.

Markdown

LLM ≠ agent

This fixed pipeline still is not an agent:

document = load_pdf()
fields = llm_extract_fields(document)
validated = validate(fields)
save(validated)

The LLM performs a semantic transformation, but application code still determines the sequence. This distinction is useful because many production AI systems need LLM capability without agentic orchestration.

Markdown

Why hybrid designs are common in production

Deterministic shell

Authentication, validation, budgets, policy, persistence, approvals, and side effects remain predictable.

Agentic island

The model handles ambiguity, exploration, semantic comparison, or adaptive investigation.

Inspectable boundary

Structured inputs and outputs make it possible to test where autonomy begins and ends.

Fallback path

The system can degrade to rules, partial results, or human escalation if the agentic part fails.

Markdown

Common architecture mistakes

Agentifying a fixed pipeline

The model chooses among steps whose order was already known, adding cost and nondeterminism without value.

Encoding ambiguity as endless rules

Hundreds of brittle branches try to approximate semantic judgment that a model could handle better.

Letting the agent own invariants

Price limits, permissions, tenant boundaries, and irreversible side effects become prompt instructions instead of code policy.

All-or-nothing thinking

Teams choose “workflow” or “agent” for an entire product instead of separating deterministic and agentic regions.
