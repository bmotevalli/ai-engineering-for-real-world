Lesson 7 — Stopping Conditions and Budgets

Module 03 · AI Agents · decide when an agent must stop, not just when the model wants to stop

Markdown

Completion and termination are different

In earlier lessons, the model could return a final answer. That is one successful stopping condition. Production agents also need host-enforced termination when continuing is no longer safe, useful, or affordable.

The model may decide that it is finished. The application decides whether it is allowed to continue.

An agent that lacks stopping conditions can loop, repeat tools, burn tokens, wait forever on dependencies, or continue acting after it has stopped making progress.

Markdown

Think of budgets as independent dimensions

Step budget

Maximum number of model decision turns.

Tool-call budget

Maximum external actions, independent of model steps and low-level retries.

Time budget

Wall-clock deadline for the whole run, plus narrower request timeouts.

Token / cost budget

Maximum model usage or estimated spend for the run.

Progress budget

Stop repeated actions or iterations that produce no new evidence.

Authority boundary

Stop when approval, permission, cancellation, or another external constraint blocks continuation.

A budget is a ceiling, not a target. A well-behaved agent should finish as soon as the goal is satisfied.

Markdown

Where the checks belong

before model call ├── deadline exceeded? ├── step budget exhausted? └── token/cost budget exhausted? ↓ model decides ↓ before tool execution ├── tool-call budget exhausted? ├── repeated action? └── permission / approval available? ↓ tool observation ↓ progress made? ├── yes → continue if needed └── no → increment no-progress counter ↓ finish or terminate with explicit reason

Checking only max_steps at the bottom of the loop is too late for many real systems.

Example 1 — make the run budget explicit

We model limits separately from usage. The budget object is configuration; the usage object is mutable host-owned state.

In [ ]
from dataclasses import dataclass
from enum import Enum
import time

class StopReason(str, Enum):
    COMPLETED = "completed"
    STEP_BUDGET = "step_budget"
    TOOL_BUDGET = "tool_budget"
    TIME_BUDGET = "time_budget"
    TOKEN_BUDGET = "token_budget"
    COST_BUDGET = "cost_budget"
    REPEATED_ACTION = "repeated_action"
    NO_PROGRESS = "no_progress"

@dataclass(frozen=True)
class RunBudget:
    max_steps: int = 5
    max_tool_calls: int = 6
    max_seconds: float = 30.0
    max_tokens: int = 8_000
    max_cost_usd: float = 0.25
    max_same_action: int = 2
    max_no_progress: int = 2

@dataclass
class RunUsage:
    steps: int = 0
    tool_calls: int = 0
    tokens: int = 0
    cost_usd: float = 0.0
    no_progress: int = 0

Centralise the deterministic checks

The model cannot increase these limits. The host can inspect them before expensive operations.

In [ ]
def check_budget(
    budget: RunBudget,
    usage: RunUsage,
    *,
    started_at: float,
    now: float | None = None,
) -> StopReason | None:
    current = time.monotonic() if now is None else now

    if current - started_at >= budget.max_seconds:
        return StopReason.TIME_BUDGET
    if usage.steps >= budget.max_steps:
        return StopReason.STEP_BUDGET
    if usage.tool_calls >= budget.max_tool_calls:
        return StopReason.TOOL_BUDGET
    if usage.tokens >= budget.max_tokens:
        return StopReason.TOKEN_BUDGET
    if usage.cost_usd >= budget.max_cost_usd:
        return StopReason.COST_BUDGET
    if usage.no_progress >= budget.max_no_progress:
        return StopReason.NO_PROGRESS
    return None
Markdown

Do not confuse provider usage with budgets

The provider may report input/output token usage after a model call. Your application records that usage and compares it with its own policy. Cost is normally derived from usage and the model's current pricing rather than trusted as a model decision.

Important: a post-call token count cannot prevent that call from exceeding a tiny remaining budget. For strict enforcement, reserve or estimate capacity before the call, then reconcile with actual usage afterwards.

Example 2 — repeated-action detection

An agent can remain under its step budget while doing the same useless thing repeatedly. Detect repetitions before executing another identical tool call.

In [ ]
import json
from collections import Counter

def action_fingerprint(name: str, arguments: dict) -> str:
    normalized = json.dumps(arguments, sort_keys=True, separators=(",", ":"))
    return f"{name}:{normalized}"

def repeated_too_often(
    fingerprints: list[str],
    *,
    max_same_action: int,
) -> bool:
    if not fingerprints:
        return False
    counts = Counter(fingerprints)
    return counts[fingerprints[-1]] > max_same_action

history = [
    action_fingerprint("get_weather", {"city": "Melbourne", "date": "2026-09-26"}),
    action_fingerprint("get_weather", {"date": "2026-09-26", "city": "Melbourne"}),
    action_fingerprint("get_weather", {"city": "Melbourne", "date": "2026-09-26"}),
]

print(repeated_too_often(history, max_same_action=2))

Expected result: True. Sorting the arguments makes semantically identical requests produce the same fingerprint.

Markdown

Repeated action is not always lack of progress

Polling a deployment status twice may be legitimate; querying the same weather endpoint three times with unchanged arguments is usually not. A useful detector combines action repetition with whether observations materially changed.

Action repetition

“Did we request the same operation again?” Easy to detect deterministically.

Observation progress

“Did the new result add evidence or change state?” Domain-specific and sometimes harder.

Keep the first implementation conservative: detect obvious loops, then add domain-specific progress signals where they provide real value.

Example 3 — stop gracefully and preserve the trace

Do not throw away everything when a budget ends. Return a structured run result that distinguishes successful completion from host-enforced termination.

In [ ]
from dataclasses import field

@dataclass
class RunResult:
    stop_reason: StopReason
    answer: str | None = None
    usage: RunUsage = field(default_factory=RunUsage)
    observations: list[dict] = field(default_factory=list)

def stopped_result(
    reason: StopReason,
    *,
    usage: RunUsage,
    observations: list[dict],
) -> RunResult:
    return RunResult(
        stop_reason=reason,
        answer=None,
        usage=usage,
        observations=observations,
    )

The caller can now choose a user-facing response: partial result, clear limitation, resumable checkpoint, or escalation. A stop condition is an expected control-flow outcome, not necessarily an exception.

What should happen when a budget is reached?

Return a partial result

Useful when the agent gathered valid evidence but did not fully complete the goal.

Ask for approval

Useful when additional cost, authority, or risky action is required. Lesson 8 develops this.

Create a resumable checkpoint

Useful for long-running work where a later process can continue from structured state.

Fail clearly

Sometimes the correct outcome is simply “I could not finish within the allowed limits.”

Markdown

Common mistakes

Only setting max_steps

A five-step agent can still make many retries, parallel tool calls, or expensive model requests.

Letting the model extend its budget

Limits are policy. A model can request more resources, but host code must decide.

Stopping without a reason

Operators and callers need to distinguish completion, timeout, cost limit, loop detection, and cancellation.

Using budget as a target

The agent should not “use all five steps.” It should stop as soon as the goal is complete.
