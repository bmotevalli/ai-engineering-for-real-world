Module 05 · Lesson 1

What is Model Context Protocol?

Build the architectural mental model before installing an SDK or connecting an AI application to external systems.

Markdown

Learning goal

Understand where MCP sits in an AI system and distinguish it from the adjacent ideas that are often conflated with it: LLMs, agents, tools, and function calling.

MCP standardises how an AI application connects to external capability providers. It does not decide whether the application should use those capabilities.
Markdown

The integration problem

An AI host may need controlled access to files, repository metadata, a database, or a domain API. If every host integrates directly with every system, each pairing needs its own discovery, message, and capability contract.

host A ── custom contract ── filesystem
host A ── custom contract ── GitHub
host B ── custom contract ── filesystem
host B ── custom contract ── GitHub

MCP introduces a shared protocol at this boundary. A server exposes a focused set of capabilities and a client speaks the protocol on behalf of a host.

Markdown

Five roles to keep separate

Host

The user-facing AI application. It owns the overall product and policy.

Client

A host component that connects to one MCP server and negotiates capabilities.

Server

An integration service that exposes selected tools, resources, or prompts.

Tool

A callable operation with a schema—for example, list pull requests.

Resource

Contextual data a client can read, such as a document or record.

Prompt

A reusable template or task definition offered by the server.

Code

Model the boundary with plain Python

The runnable notebook defines the server capability metadata using dataclasses. This is deliberately not an MCP implementation; it makes the architectural contract inspectable first.

server = McpServer(
    name="repository-context",
    tools=(Tool("list_open_pull_requests", "List open pull requests"),),
    resources=(Resource("repo://engineering-guide", "Engineering guide"),),
)

client = McpClient(name="course-host")
capabilities = client.discover(server)
Output

What discovery produces

Connected course-host → repository-context
Tools: ['list_open_pull_requests']
Resources: ['repo://engineering-guide']
Prompts: ['summarise_pull_request']

Discovery gives the host structured descriptions of what the server says it can provide. It does not grant the model direct access to the underlying repository.

Markdown

MCP vs function calling

Function calling is a model interaction pattern: a model selects a function and proposes arguments. MCP is an integration protocol: a client discovers and communicates with a capability provider.

LLM → selects tool + arguments → host policy / executor
                         ↑
            MCP client discovers tool definitions from server

An MCP-discovered tool can later be represented to an LLM as a function, but these are different layers with different responsibilities.

Markdown

Security boundary

Do not treat an MCP server as trusted authority merely because it uses MCP.

Tool descriptions, resource content, and results can be untrusted input. The host must apply authentication, authorisation, validation, consent, least privilege, execution limits, and audit logging outside the model.

Markdown

Checkpoint

  • Can you explain why a server can expose useful MCP capabilities without containing an LLM?
  • Can you distinguish capability discovery from tool authorisation?
  • Can you place MCP and function calling at their different layers?
