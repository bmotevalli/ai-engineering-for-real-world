OpenAI API

Concept overview — The Responses API is OpenAI’s unified interface for building model-powered applications. A single request can combine instructions, conversational input, tool definitions, structured output requirements, and multimodal content, while the response can contain generated text, tool calls, or other typed items. It is best understood as an application-level orchestration API rather than only a text-generation endpoint.

What this section achieves — Use OpenAI's modern API for text, structured outputs, tools, multimodal input, and agent-like workflows.

Concept overview — A chat application sends the model a sequence of messages representing instructions, user requests, and prior conversational turns. The model does not retain a conversation automatically unless the application supplies or references that state, so history management, truncation, summarisation, and streaming are application responsibilities. This pattern provides a natural user interface but still needs explicit state and cost controls.

What this section achieves — Build conversational applications with system instructions, history, streaming, and token accounting.

Concept overview — Structured output constrains a model to return data that conforms to a predefined schema, such as a JSON object represented by a Python data model. Instead of parsing loosely formatted prose, the application receives predictable fields and types that can be validated and passed safely into downstream code. This is especially useful for extraction, classification, workflow decisions, and API integration.

What this section achieves — Force model responses to conform to JSON schemas or typed data models so outputs are reliable for software integration.

Concept overview — Tool calling lets a model choose from functions described by the application and produce structured arguments for the selected function. The model proposes an action, but trusted application code validates the arguments, performs the operation, and returns the result for the model to interpret. This separates probabilistic language understanding from deterministic execution.

What this section achieves — Allow models to select and invoke application functions while your code remains responsible for actual execution and validation.

Ollama

Concept overview — Local model serving runs model inference on hardware you control and exposes it through a local process or HTTP API. Ollama packages model weights, runtime configuration, and common serving operations behind a simple developer experience, making it practical to test open models without building the inference stack from scratch. Performance and model capacity remain bounded by the available CPU, GPU, and memory.

What this section achieves — Install and run open models locally through a simple API and command-line interface.

Concept overview — Local models consist of large weight files plus configuration describing the model family, quantisation, context size, and prompt format. A model manager handles downloading, caching, versioning, loading, and removing these artefacts so developers can switch between models consistently. This is similar to package management, but the artefacts are often several gigabytes and tightly coupled to hardware limits.

What this section achieves — Pull, run, update, and remove models using a developer-friendly workflow.

Concept overview — LLM inference is dominated by large matrix operations. CPUs can run quantised models and are useful for experimentation, but GPUs provide much higher parallel throughput and memory bandwidth, which usually means faster token generation and better concurrency. The decisive constraints are not only compute speed but also accelerator memory, model size, context length, and the number of simultaneous requests.

What this section achieves — Understand how hardware affects model size, speed, concurrency, memory usage, and user experience.

Concept overview — Quantisation stores model weights using fewer bits, such as 8-bit or 4-bit values, rather than full-precision floating-point numbers. Different quantisation formats balance size, speed, hardware compatibility, and fidelity differently.

What this section achieves — Run compressed variants of larger models on commodity hardware while accepting some reduction in quality.

LiteLLM

Concept overview — LiteLLM presents many model providers through a common request and response format, usually resembling the OpenAI API. Concept overview — Model routing selects a model or provider at runtime according to policies such as task capability, latency, cost, region, tenant, rate limits, or data sensitivity. What this section achieves — Select providers or models dynamically based on cost, latency, capability, region, or tenant.

Concept overview — A fallback policy retries a request through an alternative model, region, or provider when the preferred route is unavailable or unsuitable. What this section achieves — Automatically retry with another model or provider when the preferred route fails.
