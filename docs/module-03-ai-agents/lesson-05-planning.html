Lesson 5 — Planning

Module 03 · AI Agents · when to plan, how to represent a plan, and when to replan

Markdown

Why planning exists

A reactive agent can decide one action at a time. That is often enough. Planning becomes useful when a goal has several dependencies, expensive actions, ordering constraints, or a need for user review before execution.

A plan is an explicit, revisable description of intended work — not permission to execute it.

Planning should not mean asking for hidden chain-of-thought. The useful artifact is a concise external task list: what needs to be done, in what order, and what evidence each step needs.

Markdown

Reactive loop versus plan-first agent

Reactive

observe → choose next action → execute → observe → ...

Good when the next step is obvious from the latest observation and the task is short.

Plan-first

goal → create plan → execute step → observe → update/replan → ...

Useful when coordination matters or you need an inspectable picture of intended work.

Neither is universally better. Planning adds another model call, more state, and a new failure mode: the agent can become attached to a bad or stale plan.

Markdown

Theoretical examples

Travel: “Plan a half-day outdoors in Melbourne tomorrow.” A useful plan might check weather, check daylight, choose a time window, then produce an itinerary. If heavy rain is observed, the outdoor plan may need revision.

Engineering: “Investigate why checkout latency increased.” A plan might inspect service metrics, compare dependency health, inspect the current deployment, then form a conclusion. If the first observation shows a database incident, several planned steps may become unnecessary.

When planning is unnecessary: “What is tomorrow's weather in Melbourne?” Creating a four-step plan before calling one weather tool only adds latency and cost.

Markdown

A plan belongs in state

Lesson 4 separated working state from durable memory. A plan is normally working state for the current goal. The host should track status deterministically rather than asking the model to remember which steps have completed.

Plan ├── step 1 pending → completed ├── step 2 pending → completed ├── step 3 pending → skipped └── step 4 pending → blocked Observations can cause the plan to change.
Markdown

Main example — plan a Melbourne outdoor half-day

Plan a half-day outdoors in Melbourne tomorrow. Check whether the weather is suitable and make sure the suggested time is before sunset.

We deliberately reuse familiar tools from earlier lessons. The new mechanism is the explicit plan: first create a small task list, then execute it under host control, and replan if evidence invalidates the remaining steps.

1. Represent plan steps as application data

Keep status and execution metadata outside prose so they are inspectable and testable.

In [ ]
from dataclasses import dataclass, field
from typing import Literal

StepStatus = Literal["pending", "completed", "skipped", "blocked"]

@dataclass
class PlanStep:
    id: int
    action: str
    purpose: str
    status: StepStatus = "pending"
    result: str | None = None

@dataclass
class PlanState:
    goal: str
    steps: list[PlanStep] = field(default_factory=list)
    revision: int = 0

    def pending(self) -> list[PlanStep]:
        return [step for step in self.steps if step.status == "pending"]

2. Ask for a concise external plan

The planner returns structured tasks, not private reasoning. We constrain the plan to known actions so the host can validate it.

In [ ]
import json
import os
from openai import OpenAI
from dotenv import load_dotenv

load_dotenv()
client = OpenAI()
model = os.getenv("OPENAI_MODEL", "gpt-5.6")

PLAN_SCHEMA = {
    "type": "object",
    "properties": {
        "steps": {
            "type": "array",
            "minItems": 1,
            "maxItems": 5,
            "items": {
                "type": "object",
                "properties": {
                    "action": {
                        "type": "string",
                        "enum": ["get_weather", "get_sun_times", "synthesize"],
                    },
                    "purpose": {"type": "string"},
                },
                "required": ["action", "purpose"],
                "additionalProperties": False,
            },
        }
    },
    "required": ["steps"],
    "additionalProperties": False,
}

def create_plan(goal: str) -> PlanState:
    response = client.responses.create(
        model=model,
        instructions=(
            "Create a concise external execution plan. "
            "Do not provide hidden reasoning. Use only the allowed actions. "
            "Use the minimum number of steps needed."
        ),
        input=goal,
        text={"format": {"type": "json_schema", "name": "plan", "schema": PLAN_SCHEMA, "strict": True}},
    )
    payload = json.loads(response.output_text)
    steps = [PlanStep(i + 1, item["action"], item["purpose"]) for i, item in enumerate(payload["steps"])]
    return PlanState(goal=goal, steps=steps)

3. Validate the plan before execution

A model-generated plan is untrusted application input. Reject unknown actions and plans that do not end in synthesis.

In [ ]
ALLOWED_ACTIONS = {"get_weather", "get_sun_times", "synthesize"}

def validate_plan(plan: PlanState) -> None:
    if not plan.steps:
        raise ValueError("Plan must contain at least one step")
    if len(plan.steps) > 5:
        raise ValueError("Plan is too large")
    if any(step.action not in ALLOWED_ACTIONS for step in plan.steps):
        raise ValueError("Plan contains an unsupported action")
    if plan.steps[-1].action != "synthesize":
        raise ValueError("Plan must end with synthesis")

4. Execute one planned step at a time

The planner does not execute tools. The host selects the next pending step, calls trusted code, stores the observation, and updates status.

def complete_step(step: PlanStep, result: dict) -> None:
    step.result = json.dumps(result)

        return get_weather(city, target_date)
    if step.action == "get_sun_times":
        return get_sun_times(city, target_date)
    raise ValueError(f"{step.action} is not an executable tool step")

Replanning: treat the plan as a hypothesis

Suppose the first weather observation reports severe rain. A rigid planner might continue checking sunset and constructing an outdoor itinerary anyway. A better system asks whether the remaining plan is still useful.

Plan → execute → observe → validate the plan → continue or revise.

Replanning does not mean regenerating a plan after every tool call. Only replan when evidence materially invalidates assumptions or makes remaining work unnecessary.

In [ ]
def should_replan(observations: list[dict]) -> bool:
    for observation in observations:
        rain = observation.get("precipitation_probability_max_percent")
        if rain is not None and rain >= 80:
            return True
    return False

This rule is intentionally deterministic so the replanning trigger is visible. In more ambiguous domains, the model may recommend replanning, but the host can still enforce when replanning is allowed and how often it may happen.

Markdown

Plan-execute-replan pattern

goal ↓ create concise plan ↓ validate plan ↓ execute next step ↓ record observation + status ↓ remaining plan still valid? ├── yes → next step └── no → revise plan (bounded) ↓ final synthesis

The plan is now another piece of state. It improves inspectability, but also increases orchestration complexity.

Markdown

Planning failure modes

Over-planning

A simple one-tool goal gets an unnecessary five-step plan, adding tokens and latency.

Stale plans

New evidence invalidates assumptions, but the agent keeps executing obsolete steps.

Too much granularity

Every trivial operation becomes its own step, making plans noisy and expensive to maintain.

Plan as authority

The application treats model-generated steps as permission to execute dangerous actions.

Markdown

When should you use planning?

Planning is a good fit when the task has meaningful dependencies, expensive or irreversible actions, a need for progress visibility, user approval, or several independent information-gathering steps. Prefer a reactive loop or deterministic workflow when the task is short, the sequence is already known, or planning would simply restate application logic.

Production principle: planning increases autonomy but does not transfer authority. Validate plans exactly as you validate tool calls.
