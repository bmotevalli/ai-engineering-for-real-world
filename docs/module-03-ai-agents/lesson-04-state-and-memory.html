Lesson 4 — State and Memory

Module 03 · AI Agents · what the current run knows versus what future runs remember

Markdown

The distinction that matters

Agent frameworks often use state, history, context, and memory loosely. In production systems, treating them as the same thing creates problems.

State is what the current run needs. Memory is what the application deliberately carries into a future run.

Lesson 3 already depended on state: after a tool call, the next model decision needed the earlier request and the tool observation. Lesson 4 makes that hidden requirement explicit and then adds durable memory separately.

Markdown

Four concepts that are easy to confuse

Context

The information supplied to this model call: instructions, current user request, selected history, tool results, and retrieved memory. Context is what the model can currently see.

Conversation history

A chronological record of user and assistant turns. It can be part of context, but it is not automatically authoritative application state and it does not have to be kept forever.

State

The structured information required to continue the current task correctly: goal, progress, observations, budgets, permissions, identifiers, and protocol items.

Memory

Information deliberately persisted beyond the current run and retrieved later because it may help a future task.

A useful mental model is:

persistent memory ──retrieve selected items──┐ │ current request + relevant history + state ├──→ model context │ current tool observations ─────────────────┘

The context window is therefore a delivery mechanism. State and memory are application data-management decisions.

Markdown

State is broader than chat history

Model-facing state

User messages, model outputs, tool calls, and tool observations that the next model decision needs.

Host-owned state

Step counters, permissions, request IDs, workflow status, budgets, database IDs, retry counts, and other structured metadata.

Some state belongs in model context because the model needs it to reason. Other state should remain application-owned because it controls authority or correctness.

Theoretical example — support agent

A support agent may show the model the customer's issue and the latest diagnostic result, but keep customer_id, permission level, refund limit, and audit ID as host-owned fields. Those values should not become true merely because the model says they changed.

AgentState ├── goal ├── step / max_steps ├── permissions ← host authority ├── input_items ← provider protocol history └── observations ← structured application trace
Markdown

State has a lifetime

State normally lives for as long as the task or workflow needs it. When the task ends, much of that information should disappear.

Theoretical example — deployment investigation

During an incident investigation the agent may hold pod names, log excerpts, a current hypothesis, tool errors, and the number of remaining steps. Those are useful while investigating. Six months later, replaying them into an unrelated request would usually be noise or stale evidence.

This gives us a practical test:

If this task finishes now, will this information still be useful and valid in a future task?

If the answer is no, it is probably working state rather than durable memory.

Markdown

Memory begins with a persistence decision

Memory is not simply "whatever happened before." The application decides that some information is worth preserving, stores it under an explicit scope, and later decides when to retrieve it.

Theoretical example — travel assistant

Temporary state: tomorrow's rain probability, the sunset time for this trip, the current tool call, and the remaining step budget.

Potential durable memory: the user prefers vegetarian food, avoids red-eye flights, and usually wants public transport options.

candidate information ↓ Should this outlive the task? ├── no → keep as state, then discard └── yes → validate + scope + persist ↓ retrieve when relevant ↓ revise or delete later
Markdown

Short-term and long-term are architectural choices

The terms short-term memory and long-term memory are common, but they can hide implementation details. It is clearer to ask where the data lives and how long it survives.

Run-scoped working state

Lives in process or workflow storage and is needed to continue the current execution.

Session-scoped information

May survive several turns in one session, but is intentionally discarded when the session ends.

Durable user/project memory

Survives restarts and sessions in a database, object store, document store, vector index, or other persistence layer.

Retrieved memory

The small relevant subset selected from durable storage and injected into the context for the current task.

Notice that durable storage does not imply the model sees everything in it. Retrieval is a separate decision.

Example 1 — Explicit working state

A small AgentState dataclass makes the current task inspectable. The protocol history and deterministic host metadata are related, but not the same thing.

In [ ]
from dataclasses import dataclass, field
from typing import Any

@dataclass
class AgentState:
    goal: str
    max_steps: int = 5
    step: int = 0
    input_items: list[Any] = field(default_factory=list)
    observations: list[dict[str, Any]] = field(default_factory=list)

    def __post_init__(self) -> None:
        if not self.input_items:
            self.input_items.append(
                {"role": "user", "content": self.goal}
            )

step and max_steps are host control data. The model does not get to redefine them. observations gives the application a structured trace that is easier to test and log than natural-language history.

Markdown

State dies with the task unless you persist it

Suppose the current travel task finishes. The tool outputs, temporary weather facts, and step counters are no longer needed. Throwing them away is often correct.

But a stable user preference may be worth carrying into a later task:

I prefer vegetarian food and morning departures.

That is where memory begins.

Example 2 — Durable memory across sessions

To keep the mechanics visible, the notebook uses a tiny JSON-backed memory store. A production system would usually replace the storage layer, but the contract remains the same.

In [ ]
import json
from pathlib import Path

class JsonMemoryStore:
    def __init__(self, path: Path) -> None:
        self.path = path

    def get_preferences(self, user_id: str) -> dict[str, str]:
        if not self.path.exists():
            return {}
        data = json.loads(self.path.read_text(encoding="utf-8"))
        return data.get(user_id, {})

    def set_preference(self, user_id: str, key: str, value: str) -> None:
        data = {}
        if self.path.exists():
            data = json.loads(self.path.read_text(encoding="utf-8"))
        data.setdefault(user_id, {})[key] = value
        self.path.write_text(json.dumps(data, indent=2), encoding="utf-8")

This intentionally simple store exposes the important idea: memory is application data with a lifecycle. It can be read, changed, deleted, scoped, audited, and protected independently from the model.

Compare those durable preferences with a tool observation such as rain_probability=70%. The observation may be useful now, but would become stale quickly. Persisting it as a long-term user memory would be misleading.

Markdown

Memory does nothing until the application retrieves it

A model API does not magically remember your database. The host decides what memory is relevant, retrieves it, and places it into the current context.

Durable memory store ↓ retrieve selected memory Context builder + current goal + current working state ↓ Model call

For a travel request, dietary and departure-time preferences are useful. For a code-review agent, they probably are not.

In [ ]
def build_memory_context(preferences: dict[str, str]) -> str:
    if not preferences:
        return "No saved user preferences."

    lines = [
        f"- {key}: {value}"
        for key, value in sorted(preferences.items())
    ]
    return "Saved user preferences:\n" + "\n".join(lines)

The notebook then sends this selected context into a fresh model request. The old agent state is gone. Only deliberately retained memory crosses the session boundary.

Markdown

Useful memory categories

Working / short-term

Current goal, observations, intermediate results, protocol history.

Episodic

Selected records of previous interactions or events: for example, "the user visited Kyoto last year."

Semantic

Stable facts and preferences: for example, preferred language, dietary preference, or a project's deployment region.

Procedural

Durable instructions about how work should be performed: for example, "always open a PR rather than pushing directly to production."

These labels are useful, but the production question is simpler: what data is persisted, why, for how long, and who may retrieve it?

Markdown

Why not keep every conversation forever?

Unlimited history causes context-window pressure, higher token cost, slower requests, stale or contradictory facts, privacy exposure, persistent prompt injection, and poor relevance.

More memory is not automatically a better agent. Better memory means carrying forward the minimum useful information with explicit ownership and lifecycle rules.
Markdown

Context window is not memory storage

A larger context window lets you send more information to a model. It does not solve persistence, retrieval, correction, deletion, ownership, relevance, or retention. Those are application architecture concerns.

Security note: long-term memory can persist malicious or sensitive content far beyond the request that introduced it. Treat writes to memory as a trust boundary, not as harmless chat history.
Markdown

Production checklist

Before adding durable memory, decide what qualifies for persistence; the user/tenant/project scope; how stale facts are updated; how users inspect, correct, or delete data; how secrets and sensitive information are excluded; how retrieval is authorised; and how retention affects compliance and cost.
