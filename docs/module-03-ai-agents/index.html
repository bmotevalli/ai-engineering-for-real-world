Lesson 1

What is an AI Agent?

Start with the control-flow decision that separates an ordinary LLM application from an agent.

Normal LLM application

This is simply an LLM call. It is not an agent:

User → LLM → Answer
response = model("Explain Kubernetes")

The model receives input and generates output, but it is not deciding what actions should happen next.

From a question to a goal

Investigate why my Kubernetes deployment is failing and tell me what I should fix.

A useful AI system may need to perform a sequence of investigations:

inspect deployment
       ↓
inspect pods
       ↓
read events
       ↓
read logs
       ↓
form hypothesis
       ↓
inspect configuration
       ↓
verify hypothesis
       ↓
recommend fix

The important difference is that the model can decide: What should I do next?

Engineering definition of an AI agent

An AI agent is a system where an LLM participates in choosing the next action required to achieve some goal.

This definition is intentionally practical rather than marketing-oriented. It tells us where to look in the architecture: at the point where control flow is chosen.

The agent loop

Observe
   ↓
Decide
   ↓
Act
   ↓
Observe result
   ↓
Decide again

The loop continues until the goal is completed, the agent cannot progress, or a stopping condition is reached.

Workflow vs agent

Deterministic workflow

logs = get_logs()
errors = analyse_logs(logs)
report = generate_report(errors)

The application controls the execution order.

VS

Agent

The model participates in choosing what action should happen next based on what it has observed.

The important question is:Where is the model making an autonomous control-flow decision?

Four core components of an agent

1

Goal

An agent works toward a goal rather than merely responding to one isolated prompt.

2

LLM

The LLM is the decision-making component that can choose whether to answer, gather more information, or try another approach.

3

Tools

Tools expose external capabilities such as APIs, databases, GitHub, search, or calculators.

4

State

State captures what the agent has learned and done while solving a task.

Simple agent example

Give an agent two tools: get_weather(city) and get_current_time(city).

Tell me whether this evening would be good for an outdoor run in Perth.

The model may choose to call weather first, then time, then decide it has enough information to answer. The important point is that the model chooses part of the control flow.

Where RAG fits

RAG is not required for agents. Retrieval can simply be one tool among many, such as document search, web search, a database query, GitHub, or Python execution.

Lesson 2 In progress

Tool Calling from Scratch in Python

Understand one complete tool-use turn before we introduce a full agent loop.

What this lesson is about

Tool calling gives an LLM a structured way to request an action from your application. The model can choose a tool and propose arguments, but your Python code remains responsible for validating, authorising, executing, and returning the result.

The model proposes an action. Your application decides whether and how that action is executed.

The mental model

1 · DescribeHost sends tool schema
2 · DecideModel requests a tool
3 · ValidateHost checks arguments
4 · ExecuteHost runs trusted code
5 · ObserveModel receives the result

This boundary is fundamental for reliability and security. Tool definitions describe capabilities; they do not give the model direct executable access.

What you should understand before the exercise

  • A tool definition is a contract shown to the model.
  • The tool implementation is ordinary trusted application code.
  • Model-generated arguments are untrusted input.
  • The host should dispatch only allowlisted tools.
  • call_id correlates a tool result with the model request.
  • One tool-use turn is still a bounded workflow, not yet a general agent loop.

Example briefing — service health assistant

Imagine a small operations assistant. A user asks:

Is checkout healthy in production?

The LLM cannot know the current health of the service from its training data. We therefore expose a deterministic tool named lookup_service_health. The model sees the tool description and parameter schema, decides whether the tool is relevant, and proposes arguments such as service="checkout" and environment="production".

The Python host then validates those arguments, executes the trusted function, sends the observation back to the model, and asks the model to explain the result to the user. The exercise intentionally permits only one tool-use turn so you can clearly see every boundary before Lesson 3 introduces repetition.

Important production idea

Treat both directions as untrusted

Model-generated tool arguments are untrusted input to your application. Tool results are also untrusted input to the model and can contain misleading or injected instructions. Validate, minimise, authorise, and log data crossing the boundary.

Checkpoint

Does tool calling make this an agent?

Not by itself. In this lesson the model may choose whether to request one available action, but the host still enforces a bounded workflow. Lesson 3 turns the same mechanism into an explicit repeated agent loop.

Who owns permissions and side effects?

The host application. Authentication, authorisation, approval, rate limits, timeouts, and idempotency belong around the real tool implementation.

Lesson 3 — The Agent Loop

We will turn the bounded exchange into an explicit loop that can process zero, one, or several tool-use turns while preserving state and enforcing a step budget.

for step in range(max_steps):
    response = model.decide(state)
    if response.is_final:
        return response.answer
    observations = execute_requested_tools(response)
    state.extend(response, observations)

That introduces termination, repeated calls, partial failure, observability, and what the host should do when the model does not finish.
