Lesson 1

What is an AI Agent?

Start with the control-flow decision that separates an ordinary LLM application from an agent.

Normal LLM application

This is simply an LLM call. It is not an agent:

User → LLM → Answer
response = model("Explain Kubernetes")

The model receives input and generates output, but it is not deciding what actions should happen next.

From a question to a goal

Investigate why my Kubernetes deployment is failing and tell me what I should fix.

A useful AI system may need to inspect deployments, pods, events, logs, configuration, and evidence before deciding what to do next.

Engineering definition of an AI agent

An AI agent is a system where an LLM participates in choosing the next action required to achieve some goal.

The agent loop

Observe
   ↓
Decide
   ↓
Act
   ↓
Observe result
   ↓
Decide again

The loop continues until the goal is completed, the agent cannot progress, or a stopping condition is reached.

Workflow vs agent

Deterministic workflow

The application determines the execution order in advance.

VS

Agent

The model participates in choosing what action should happen next based on what it has observed.

The important question is:Where is the model making an autonomous control-flow decision?

Four core components of an agent

1

Goal

An agent works toward a goal.

2

LLM

The LLM participates in decisions.

3

Tools

Tools expose external capabilities.

4

State

State captures what the agent has learned and done.

Lesson 2 Completed

Tool Calling from Scratch in Python

Understand one complete tool-use turn before we introduce a full agent loop.

What this lesson is about

Tool calling gives an LLM a structured way to request an action from your application. The model can choose a tool and propose arguments, but your Python code remains responsible for validating, authorising, executing, and returning the result.

The model proposes an action. Your application decides whether and how that action is executed.

The mental model

1 · DescribeHost sends tool schema
2 · DecideModel requests a tool
3 · ValidateHost checks arguments
4 · ExecuteHost runs trusted code
5 · ObserveModel receives the result

This boundary is fundamental for reliability and security. Tool definitions describe capabilities; they do not give the model direct executable access.

What you should understand before the examples

  • A tool definition is a contract shown to the model.
  • The tool implementation is ordinary trusted application code.
  • Model-generated arguments are untrusted input.
  • The host should dispatch only allowlisted tools.
  • call_id correlates a tool result with the model request.
  • One tool-use turn is still a bounded workflow, not yet a general agent loop.
Example 1 · Everyday

Weather assistant with a real API

Imagine a small travel assistant. The user asks:

Will I need an umbrella in Melbourne tomorrow?

This is an approachable tool-calling problem because everyone understands the question, but the model cannot safely know tomorrow's live weather from its training data. The example exposes a read-only get_tomorrow_weather tool backed by the public Open-Meteo API.

The model decides whether live weather is needed and proposes the city. Python validates the request, resolves the city, calls the weather API, returns the forecast as an observation, and the model converts that data into a useful recommendation.

Example 2 · Engineering

Service health assistant

Once the tool-calling mechanics are familiar, the second example applies exactly the same pattern to an engineering scenario:

Is checkout healthy in production?

The model cannot know current production telemetry from its training data, so the host exposes lookup_service_health. This example goes deeper into allowlists, validation, unknown states, trusted execution boundaries, and production-oriented failure handling.

The important connection is that the underlying protocol is unchanged: model chooses a capability → host validates and executes → observation returns to the model.

Important production idea

Treat both directions as untrusted

Model-generated tool arguments are untrusted input to your application. Tool results are also untrusted input to the model and can contain misleading or injected instructions. Validate, minimise, authorise, and log data crossing the boundary.

Lesson 3 In progress

The Agent Loop

Turn one tool-use turn into repeated model decisions under host-controlled limits.

What changes from Lesson 2?

Lesson 2 forced the model to stop after one tool call. In a real agent loop, the model gets another decision after every observation. It can answer, request another tool, recover from a tool error, or continue gathering evidence.

The model proposes the next action; the application owns the control loop.

The loop

Goal
 ↓
Model decides
 ↓
Action requested
 ↓
Host validates + executes
 ↓
Observation added to state
 ↓
Model decides again
 ↓
... until final answer or host limit

The host still owns permissions, execution, state updates, and stopping conditions. The new autonomy is specifically that the model participates in deciding what happens next.

Learning outcomes

  • Recognise final-answer versus tool-request states.
  • Preserve model outputs and tool observations between turns.
  • Understand why observations change the model's next decision.
  • Enforce a step budget from the first implementation.
  • Return tool failures as observations without surrendering host control.
  • Explain why the same loop can support new tools without hard-coded branching.
Main exercise · Everyday

Multi-step Melbourne travel assistant

The user asks:

I'm visiting Melbourne tomorrow. Will I need an umbrella, and what time is sunset?

The assistant has two live, read-only tools: get_weather and get_sun_times. Both use Open-Meteo. The Python code does not prescribe an order such as weather → sunset. Instead, it repeatedly asks the model what to do next, executes an allowed action, records the observation, and asks again.

The notebook makes the agent trace visible and includes exercises for one-tool goals, tool failures, and deliberate step-budget exhaustion.

Production idea introduced now

Do not build an unbounded agent loop

Even this first implementation uses max_steps. Production systems may also bound wall-clock time, token/cost budget, tool calls, permissions, or require human approval. Autonomy is useful only inside explicit host-controlled limits.

Engineering extension

The same loop can move from service health to incident details: health check → observe incident ID → model chooses incident lookup → observe incident → final explanation. The control loop itself does not change.

Checkpoint

What makes this more agentic than Lesson 2?

The model repeatedly chooses the next action after seeing new observations. Python no longer prescribes a fixed sequence, although it still controls what actions are allowed and when execution must stop.

Is the accumulated state long-term memory?

No. It is working state for the current run. Lesson 4 separates working state, conversation history, short-term memory, and durable memory.
