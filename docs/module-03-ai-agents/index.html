Lesson 1

What is an AI Agent?

Start with the control-flow decision that separates an ordinary LLM application from an agent.

Normal LLM application

This is simply an LLM call. It is not an agent:

User → LLM → Answer
response = model("Explain Kubernetes")

The model receives input and generates output, but it is not deciding what actions should happen next.

From a question to a goal

Investigate why my Kubernetes deployment is failing and tell me what I should fix.

A useful AI system may need to inspect deployments, pods, events, logs, configuration, and evidence before deciding what to do next.

Engineering definition of an AI agent

An AI agent is a system where an LLM participates in choosing the next action required to achieve some goal.

The agent loop

Observe
   ↓
Decide
   ↓
Act
   ↓
Observe result
   ↓
Decide again

The loop continues until the goal is completed, the agent cannot progress, or a stopping condition is reached.

Workflow vs agent

Deterministic workflow

The application determines the execution order in advance.

VS

Agent

The model participates in choosing what action should happen next based on what it has observed.

The important question is:Where is the model making an autonomous control-flow decision?

Four core components of an agent

1

Goal

An agent works toward a goal.

2

LLM

The LLM participates in decisions.

3

Tools

Tools expose external capabilities.

4

State

State captures what the agent has learned and done.

Agent autonomy is a spectrum

DeterministicAutonomous
LLM callFixed workflowTool selectionIterative tool selectionPlanningPlan adaptationLong-running autonomous agent
Engineering principleUse the minimum level of autonomy necessary to solve the problem well.

State and Memory

Separate what the current agent run needs from what the application deliberately remembers across future runs.

The key distinction

State is what the current run needs. Memory is what the application deliberately carries into a future run.

The distinction is about lifetime and ownership, not just storage. State normally exists to complete the current task. Memory exists because the application has decided some information should survive and may be useful later.

Four concepts that are easy to confuse

Context

Everything supplied to the current model call: instructions, current request, selected history, tool observations, and retrieved memory.

Conversation history

The chronological user/assistant exchange. It can be part of context, but it is not the same thing as authoritative application state.

State

The structured information needed to continue the current task correctly: goal, progress, observations, budgets, permissions, and protocol items.

Memory

Information deliberately persisted beyond the current run and retrieved later when relevant.

Think in lifetimes

A useful question is: if this task finished now, should this information still exist for a future task?

Usually state

Current weather result, active tool call, current hypothesis, remaining step budget, temporary error, current workflow status.

Potential memory

Preferred language, dietary preference, project deployment region, recurring travel preference, or another stable fact with clear future value.

Example: a deployment-investigation agent may need pod names, logs, and a current hypothesis during the incident. Those facts are useful working state, but replaying them months later into an unrelated investigation would usually be stale noise.

Memory has a lifecycle

candidate information
       ↓
Should it outlive this task?
   ├── no  → keep as state → discard when done
   └── yes → validate + scope + persist
                         ↓
                 retrieve when relevant
                         ↓
                  revise / expire / delete

Persistence alone does not make a useful memory system. The application also needs rules for scope, retrieval, relevance, correction, deletion, retention, and authority.

Theoretical example — travel assistant

For the question “Plan my Melbourne day tomorrow”, the assistant may use tomorrow's rain probability and sunset time as current state. But a preference such as “I prefer vegetarian restaurants and morning departures” may be worth remembering across future sessions. The two types of information belong to different lifecycles even though both may appear in the same model context today.

Production principle

Do not treat unlimited conversation history as memory

Long-term memory should be selected, scoped, revisable, and deletable. Persisting everything increases token cost, stale-context risk, privacy exposure, and the chance that malicious instructions survive far beyond the request that introduced them.

Planning

Decide when an agent should create an explicit plan, how the plan lives in state, and when new evidence should revise it.

Core idea

A plan is an explicit, revisable description of intended work — not permission to execute it.

A reactive agent chooses one action at a time. Planning adds a separate artifact: a concise task list that can expose dependencies, ordering, progress, and work that may need approval before execution.

When planning helps

  • Several dependent information-gathering steps.
  • Expensive or irreversible actions.
  • Need for progress visibility or user review.
  • Tasks where observations may invalidate later work.
  • Do not plan merely because the system is agentic.
  • Simple one-tool questions are usually better without a plan.
  • Known fixed sequences are often deterministic workflows.
  • Planning adds model calls, latency, state, and failure modes.

Planning is not chain-of-thought

The useful artifact is a short external task list: what needs to happen, which allowed action it maps to, and what evidence is needed. The application does not need private model reasoning in order to execute safely.

The plan-execute-replan pattern

goal
 ↓
create concise plan
 ↓
validate plan
 ↓
execute next step
 ↓
record observation + status
 ↓
remaining plan still valid?
 ├── yes → continue
 └── no  → revise / skip (bounded)
 ↓
final synthesis

The plan is working state. The host owns allowed actions, step status, tool execution, and limits on replanning.

Engineering extension

For “Investigate why checkout latency increased”, an explicit plan might inspect service metrics, dependency health, and the current deployment before synthesis. If the first observation reveals a known database incident, the host can skip or revise steps that no longer add value.

Production principle

Planning increases autonomy, not authority

A model-generated plan is untrusted application input. Validate allowed actions and plan size before execution, and bound how often the system can replan.

Checkpoint

Should every agent create a plan first?

No. Planning is useful only when decomposition or coordination adds value. A one-tool weather lookup usually needs no explicit plan.

When should a plan change?

When new observations materially invalidate assumptions, make remaining work unnecessary, or block the current route. Replanning after every step is usually wasteful.
